# Ophir Domain Model v1

> **Status:** Draft for implementation and legal/accounting review

## 1. Purpose

This document defines the canonical business entities, relationships and state machines for the first Ophir product. The model is deliberately asset-agnostic and provider-agnostic. Banks, stablecoins, tokenized funds and later traditional securities all map into the same internal treasury model.

The first implementation target is a Belgian company using bank aggregation plus one regulated money-market-fund provider.

---

## 2. Core design principles

1. **Legal entity first.** All positions, rules, approvals and documents belong to a specific company/legal entity.
2. **Provider data is never the source model.** External data is normalized into Ophir entities while retaining full source lineage.
3. **Money calculations are deterministic.** Decimal arithmetic only; never floating point.
4. **Accounting/tax outputs are proposals until validated/approved.**
5. **Transactions and audit events are append-only.** Corrections are new events, not destructive edits.
6. **Execution is external.** Ophir records intent, approval, handoff and outcome; the licensed provider executes.
7. **Rules are effective-dated.** Tax/accounting/legal logic must preserve historical applicability.

## 16. Critical state-machine invariants

1. A `transaction_intent` cannot become `APPROVED_FOR_HANDOFF` unless its active approval policy is satisfied.
2. `HANDED_OFF` means only that the user crossed into a provider execution flow; it does not mean a transaction executed.
3. `COMPLETED_EXTERNALLY` requires independent provider/evidence confirmation.
4. A settled economic event may never be destructively edited; reversal/correction creates new events.
5. A tax or accounting output always references exact rule versions and input event ids.
6. A rule version cannot be edited after it has produced a finalized output; publish a new version instead.
7. AI-generated text may explain a rule evaluation but may not overwrite the deterministic result.
8. A position must reconcile to its event history within configured tolerance.

## 17. MVP persistence recommendation

PostgreSQL with:
- UUID primary keys;
- `numeric` for financial values;
- explicit currency codes;
- `timestamptz` timestamps;
- JSONB only for provider payload snapshots and structured rule facts, not as a substitute for core relational modelling;
- row-level tenant/legal-entity isolation where useful;
- append-only tables or DB protections for audit/economic events;
- migrations committed to source control.

Object storage stores original evidence and generated documents; the relational model stores metadata, hashes and references.
